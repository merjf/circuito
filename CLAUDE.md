# circuito — working notes for AI assistants

React Native (Expo Router) interval-training app. Read this before touching `src/components/`, especially `ui.tsx`.

## Shared component library — extend, don't clone

`src/components/ui.tsx` is the app's design system: buttons, chips, icon buttons (`BinButton`/`PencilButton`/`SaveButton`), steppers, cards, media handling. `ConfirmDialog`, `ActionSheet`, `StepEditSheet`, `ValueEditSheet`, and `ExercisePicker` are the app's only overlay primitives — every dialog/sheet/confirm flow routes through one of these five. No screen should ever import `Modal` or call `Alert.alert` directly; if you're about to, use or extend one of the five instead.

**Guardrail:** when a screen needs a variant of an existing shared primitive that doesn't quite exist yet — a smaller icon button, a destructive-styled CTA, a circular delete button — extend that primitive's props in `ui.tsx` in the same change, rather than hand-styling a local lookalike `Pressable`/`TouchableOpacity`. This has already happened three times in this codebase (a hand-rolled destructive "Delete" button in `session/[id].tsx`, a bespoke 28×28 block-delete `×` in `training/[id]/builder.tsx`, a third circular delete button in `exercise/[id].tsx` — all soft-red, all duplicating `BinButton`'s color logic because `IconButton` had no `size`/`shape` prop to cover the smaller/circular cases). Before building a bespoke button, check whether `IconButton`, `BinButton`, `PencilButton`, `SaveButton`, `PrimaryButton`, `SecondaryButton`, or `HeaderAction` already covers the shape — and if it's close but not quite, add the missing prop there first.

`ConfirmDialog` is for yes/no (or yes/no/destructive) prompts only — its own doc comment says so. A "pick one of N" flow (a sound picker, a filter menu, a sort menu) belongs in `ActionSheet`, not `ConfirmDialog`, even though `ConfirmDialog` will technically render an arbitrary list of `actions`.

## `AnimatedPressable` / `RepeatingPressable` — style AND animation are split across two nodes, on purpose

Both are built as an outer, animated `Pressable` (`Animated.createAnimatedComponent(Pressable)`, module scope — never recreate this inside a component body, it'd remount the subtree every render) wrapping a plain inner `View`. As of 2026-08-26 (PLAN_ui_polish.md §3.3, finding "F1") **the outer node carries both the paint AND the animation**:

- The outer `Pressable` gets the **full** `style`, PLUS the animated depth style (scale/translateY/opacity/shadowOpacity/elevation, all driven by one `pressProgress` shared value) — it's the actual flex item in whatever row/column contains the button, so any sizing prop (`flex`, `height`, `width`) has to land there or Yoga has nothing to size against, AND it's the node that actually paints background/border/radius/shadow, so it has to be the one that visibly moves on press.
- The inner `View` gets a **layout-only** copy (via the internal `layoutOnlyStyle()` helper) — `flexDirection`/`alignItems`/`gap`/etc, so multi-child buttons (e.g. a thumbnail + text + badge row) still arrange correctly — but never border/background/radius/shadow, because both nodes render at the identical rect and painting the same chrome on both stacks two coincident layers. For solid colors that's just wasteful; for any semi-transparent `rgba(...)` border or fill (this app's hairline borders and soft-red/orange/green tints), it visibly composites to a darker/more saturated edge than the design intends. It is a plain `View`, not an `Animated.View` — nothing animates on it.

**Two regressions this history fixes, in order:**

1. (2026-08-25) The original implementation applied `style` to the inner animated node only. That silently worked for any button using a fixed `height`, but broke the moment a caller needed `flex: 1` from a row parent — `ConfirmDialog`'s Cancel/Delete/OK button row collapsed to near-zero-height horizontal slivers. Fixed by moving the full `style` to the outer `Pressable`.
2. (2026-08-26) That fix moved `style` (paint) to the outer node but left the press *animation* on the inner one — which `layoutOnlyStyle()` strips all paint keys from. So pressing `PrimaryButton` shrank the white label while the dark fill sat still; the button didn't visibly respond, its text did. Fixed by moving the animation to the same outer node that paints — see F1 above.

**If you're touching `AnimatedPressable`/`RepeatingPressable` again:** keep the two-node split, and keep BOTH paint and animation on the outer node. Don't move animation back onto a separate inner node — that's regression 2. Don't move `style` back onto the inner node — that's regression 1. If you add a new paint-style property to the codebase's vocabulary (a new border/shadow/fill key), add it to `PAINT_KEYS` in `ui.tsx` too, or it'll double-paint on the inner node.

**When adding a new button/row that composes `AnimatedPressable` with multiple children:** the layout props (`flexDirection`, `gap`, `alignItems`) you pass via `style` will correctly reach the children (they're laid out inside the inner `View`). You don't need to do anything special — this is handled by the shared component now, not by each call site.

## Depth / shadows — geometry is frozen, only opacity and elevation animate

`src/theme/tokens.ts` exports an `elevation` scale (`e0`–`e4`) that replaces the old single `shadow.button`/`shadow.sheet` pair (kept as a deprecated alias — don't add new call sites against `shadow`, use `elevation` directly). Shadow **geometry** (`shadowOffset`, `shadowRadius`) is frozen per level and never animated — iOS re-rasterises a layer shadow's alpha channel offscreen on any frame that geometry changes, which is the expensive case. Only `shadowOpacity` (iOS, continuous) and `elevation` (Android, stepped — two discrete values, never tweened) animate; `transform` (scale + translateY) carries the depth read the eye actually notices. `AnimatedPressable`'s `depth` prop (`'none' | 'sink' | 'lift'`) is the only place this should be driven from — don't hand-roll a new animated shadow elsewhere.

A shadowed node needs an opaque `backgroundColor` (Android draws nothing without one; iOS traces the shadow from content alpha instead of the box) and must not have `overflow: 'hidden'` on the SAME node as the shadow (cancels the Android shadow — clip on an inner wrapper if a child needs clipping).

## Haptics — always through `src/feedback/haptics.ts`

Nothing else should import `expo-haptics` directly. Call `haptic(kind)` with one of the semantic kinds (`'tap' | 'select' | 'pickup' | 'confirm' | 'success' | 'warning' | 'error'`) — this is what keeps a destructive action feeling different from an ordinary tap without every call site re-deciding which raw `ImpactFeedbackStyle` means what. `AnimatedPressable`/`RepeatingPressable`/`IconButton`'s `haptic` prop accepts either a `Haptic` string or a `boolean` (back-compat: `true`→`'tap'`, `false`→`'none'`) — prefer the explicit string for new code. The module keeps the synchronous-throw guard around the native call (an unlinked native module throws before returning a promise, which on Hermes release builds can otherwise abort the rest of a press gesture) and a ~40ms throttle so a double-fired press-in doesn't stack two buzzes.

## Reduced motion

Any future entrance (`entering=`) or layout (`layout=`) animation must carry `.reduceMotion(ReduceMotion.System)` (Reanimated). Press scale/opacity/depth feedback is exempt — it's sub-100ms feedback, not decoration, and stays on even with Reduce Motion enabled.

## Drag-to-reorder — `DraggableList.tsx`, two entry points sharing one worklet path

The builder's exercise rows support two ways to start a drag (PLAN_ui_polish.md §7): the drag HANDLE's own immediate `Gesture.Pan()` (no hold delay — the original way), and the WHOLE ROW, which only activates after a 350ms hold (`motion.dragHold`) via `.activateAfterLongPress()`. Both are separate `GestureDetector`s (handle nested inside row) rather than a `Gesture.Exclusive` composition, and both call the exact same `begin`/`update`/`finish` worklet functions defined once per `Row` — never duplicate that logic per entry point, or the two ways to grab a row will drift apart in feel.

**Traps if you touch this file:**
- The two `Gesture.Pan()` objects (`grabPan`/`holdPan`) are memoised on `[index, count]` only. `setDragging(true)` in the parent triggers a re-render mid-gesture; rebuilding a fresh `Gesture` object on that render tears down the in-flight gesture. Don't add anything else to those dependency arrays without checking this.
- `onFinalize` is a required safety net, not redundant with `onEnd`: RNGH fires `onFinalize` (not `onEnd`) when a gesture is cancelled outright (parent ScrollView steals the responder, navigation away, an incoming call) — without it, a cancelled drag leaves the row stuck raised forever (PLAN_ui_polish.md finding "F2"). The `finish()` worklet guards on `activeIndex.value === index` so a second call after the row already settled is a safe no-op.
- Every row's `LinearTransition` is suspended list-wide (`anyDragging`, not just the dragged row's own state) while ANY row is mid-drag — otherwise every other row tries to spring to its new position while the dragged row is being translated by the gesture, and the two animations fight, leaving visible drift after release.
- The two nested `Animated.View`s per row are deliberate: gesture-driven `transform`/shadow live on the INNER node, `layout` goes on the OUTER one. Collapsing them back to one node reintroduces the drift bug above.

## Sheet/dialog motion — custom exit animation must outlive the `Modal`'s own `visible` flip

`ConfirmDialog`, `ActionSheet`, `StepEditSheet`, and `ValueEditSheet` all replaced their RN `Modal`'s `animationType` (`"fade"`/`"slide"`) with Reanimated `entering`/`exiting` (PLAN_ui_polish.md §8) — `FadeIn`/`FadeOut` for the two dialogs-that-fade, `SlideInDown`/`SlideOutDown` for the two sheets-that-slide. All four share one shape, because `Modal` has no exit-animation concept of its own to wait on:

- The scrim and the panel are rendered **conditionally** on the caller's own visibility signal (`visible` for `ConfirmDialog`/`ActionSheet`; `context != null` for `StepEditSheet`/`ValueEditSheet`) — `exiting` only plays on a Reanimated node that is actually removed from a tree that stays mounted around it, never from a prop change on a node that keeps rendering. Don't try to drive the same effect by mutating a style prop on an always-mounted node — that doesn't trigger `exiting` at all.
- A local `rendered` boolean (`useState`, seeded from the visibility signal) is what keeps the outer `<Modal visible>` itself mounted for the length of the exit animation. It flips back to `false` only inside `handleExitDone`, wired via `FadeOut(...).withCallback(handleExitDone)` on the scrim's own animated node — never on a fixed `setTimeout`, which could drift out of sync with `motion.sheetOut` (180ms) as that token changes.
- `StepEditSheet`/`ValueEditSheet` are driven by a `context` object going straight to `null`, not a boolean — so they additionally hold `lastContext` (the most recent non-null value) purely so the JSX has something to render (`shown = context ?? lastContext`) while the exit animation plays. Every reference to the context's fields in the render body must read `shown`, not `context`, or the exit frame throws on the first render after close.
- `ActionSheet`'s existing `InteractionManager.runAfterInteractions(action.onPress)` sequencing (queued the instant a row is pressed, before the sheet visually finishes closing) is unaffected by this — if anything it's safer now, since the `Modal` stays mounted for `motion.sheetOut` after `onClose()` fires, which is more than enough time for the queued callback to run before a caller's next `ConfirmDialog` opens. Keep that ordering if you touch this file: a caller opening a second overlay from a sheet action must still do so after the first sheet is gone, never simultaneously (two `Modal`s at once is unreliable on iOS).
